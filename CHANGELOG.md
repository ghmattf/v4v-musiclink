Format based on [Keep a Changelog](https://keepachangelog.com/); versions follow [Semantic Versioning](https://semver.org/) and are tracked independently per plugin.

## Resolver (v4v-musiclink) — [1.22.29] - 2026-10-06

### Added

- **Per-app icon background colour** — each music app gains a **Background** column in the Settings → Music apps table (table widened to 900px): a native colour swatch plus a "None (transparent)" tickbox, with the 32px icon preview updating live as either changes (the values are saved only by "Save Changes"). The block-editor preview shows the colour automatically because it runs the real render path. No change when unset: byte-identical markup. README settings bullets updated; `test_stored_links` grew 358 → 384 (13 pins per plugin: save precedence, settings column/inputs/preview, front-end style for the configured app only, junk and unset cases).

### Removed

- **The standard plugin no longer discovers Fountain deep links itself** — automatic Fountain resolution is now Pro-only. The standard plugin now never issues HTTP to fountain.fm: its Fountain button renders a deep link already stored on the cache row when one exists (manual Cache-tab entries and rows written by earlier versions), otherwise the quoted-search fallback added in 1.22.26 (or `fountain.fm/discover` when no title is known) — so Cache-tab editing is now the only way the standard version gains a deep link. ## Resolver (v4v-musiclink) — [1.22.24] - 2026-10-05

### Fixed
- **Fountain buttons deep-link again instead of falling back to `fountain.fm/discover` — self-heal now probes every detected action id rather than trusting the first one.** Fountain publishes several near-"search" hex ids at once (typically an older or unrelated action listed first) and rotates them on every deploy, but `fountain_autodetect_next_action()` returned only the **first** candidate and `fountain_resolve()` verified only that one: when the first was dead, the plugin POSTed a dead id, got a 200 whose body carried no `hits`, correctly refused to persist it, left the stale stored value in place and re-derived the same dead id every 15 minutes - forever, which is why every Fountain button rendered the discover fallback (`fountain_live_test.php` 0/20 from 2026-10-01). Detection is now `fountain_autodetect_next_actions()`, which returns **every** candidate as an ordered, de-duplicated list (chunk order, then file order), and `fountain_resolve()` walks that list probing each id, persisting via `update_option()` the first one that answers with a readable hits payload - never a 404, silent or unparsable one, so a dead candidate still cannot corrupt the stored id, and a miss cached for candidate #1 does not block candidate #2 (those caches are keyed per id). Two related corrections ride along: a candidate whose readable hits payload simply lacks our guid **is** persisted (it is demonstrably a live search action, so the crawl stops instead of repeating every 15 minutes on a release Fountain does not index), and an already-live stored id now ends the attempt immediately instead of triggering a re-crawl. `last_fountain_hits_parsed` is reset at the top of `fountain_try_resolve()` so it always describes the current attempt - a cached miss, 404 or transport error can no longer leave a previous attempt's "parsed" verdict behind and mislead the persist decision. The chunk walk keeps its old cost profile by staying two-phase: the handful of search-only delta chunks (where the registration lives) are walked in full, and the homepage's historic first 20 - the big framework bundles, which have held zero candidates since 2026 - are walked only when the delta found nothing; a full-window walk was measured at 34 s / 1.4 MB inline in a visitor's render versus 10 s with the phase gate. Verified live: `fountain_live_test.php` **20/20** (0/20 before), and the ids rotated twice during the release run alone, with the working id being the *second* candidate both times - which is exactly what "first candidate wins" could never find. `fountain_fix_test.php` is rewritten for probe-all-candidates (104 -> 156 assertions: scan-order/de-dup matrix plus a resolve matrix covering dead-first, all-dead, live-no-match, stored-dead, stored-live and stored-working paths), and the stale homepage-only port `tmp/fountain_probe.php` is retired in favour of the live diagnostics (`probe_sweep`, `probe_candidates`, `probe_autodetect_trace`, `probe_woman`).

## Resolver (v4v-musiclink) — [1.22.23] - 2026-10-04

### Fixed
- **A Music Index lookup left over from before the cache-table migration is no longer read as a remembered miss, so a release renders its track again instead of falling back to the album.** 1.22.21 moved the positive Music Index transients into the cache table but kept their key — `mi_track_v4_…` / `mi_feed_v4_…` — for remembered misses alone, and the "is a miss remembered?" test is presence-based. On a site that upgraded with a positive still live under that key (they run for 12 hours after the last pre-upgrade view), its own good data was treated as "this guid does not resolve": every lookup returned null, no cache row was written, the page fell back to the feed and rendered the album title alone (or "Album/Song not found" when the feed key held one too), and `queue_mi_refresh()` — which uses the same presence test — refused to queue the background pull that would have repaired the row. The key is now read by a new `mi_take_legacy_positive()`, which tells a legacy payload (a non-empty array with `title`) apart from a genuine miss (`array()`): a legacy positive is returned to the caller — so the lookup succeeds without an API round trip and the caller's store migrates it onto the cache row where it belongs — and is deleted on the way out, so the key cannot be misread again; the same clearing happens before the two presence tests in `queue_mi_refresh()` and `run_queued_mi_refresh()`, so the background refresh is no longer blocked either. Remembered misses keep short-circuiting exactly as before.

## Resolver (v4v-musiclink) — [1.22.21] - 2026-10-04

### Added
- **The "Stored links" table is now the plugin's own cache table — `{prefix}v4v_musiclink_cache` (schema 1) — and the admin tab is relabeled "Cache"**: one row per release, still keyed on the unchanged `sha1(album_guid|track_guid)`, now carrying BOTH halves of what a render needs. The Music Index half gained a new `image_url` art column and a new `mi_updated_at` stamp (when that metadata was last pulled); the Fountain half keeps its permanent link (`fountain_url`, never stale, never auto-refreshed) and its timestamp, renamed `updated_at` → `fountain_updated_at` so the two cannot be confused. The tab lists Artist, Album title, Track title, Album GUID, Track GUID, Art (a small lazy-loaded thumbnail linking to the full image), Fountain.fm link, **MI updated** and **Fountain updated**, in that order (empty row colspan 8 → 10); inline editing stays Fountain-URL-only (the MI fields are read-only, because the next pull would overwrite a hand edit), per-row delete and the two Clear scopes keep their exact semantics — the per-app clear now stamps `fountain_updated_at` — and the confirmations, notices and empty states say "cache" rather than "saved links". Existing installs migrate on the next load: the legacy v1→v2 fixup runs first, the new table is created, and every row of the old `v4v_musiclink_stored_links` table is copied across with its hash intact (`image_url = ''`, `mi_updated_at = NULL`), so the first view after the upgrade serves the copied titles immediately and fills art in the background rather than blocking; the old table and its version option are only dropped once the copy has happened. `LINKS_TABLE_VERSION`/`maybe_create_stored_links_table()` and the whole `stored_link*` family move to cache vocabulary: `CACHE_TABLE_VERSION`, `maybe_create_cache_table()`, `migrate_legacy_links_table()`, `create_cache_table()`, `cache_row_hash()`, `cache_get_row()`, `get_cached_fountain_url()`, `store_fountain_link()`, `cache_filters()`, `cache_admin_url()`, `redirect_to_cache_tab()`, `render_cache_tab_content()`, handlers `handle_update_cache_row()` / `handle_delete_cache_row()` / `handle_clear_cache()` with matching `admin_post_v4v_musiclink_{update,delete}_cache_row` / `..._clear_cache` actions and nonces, option `v4v_musiclink_cache_table_version`, and the tab slug `tab=links` → `tab=cache`.
- **A "Music Index refresh" setting on the Settings tab** (option `v4v_musiclink_mi_refresh_hours`, number field, default 12 hours, clamped 1–720 = 1 hour .. 30 days) decides when cached Music Index metadata is refreshed in the background. It is refresh-only: cached data keeps serving at any age and is never cleared by this value — lower is fresher metadata, higher is fewer Music Index requests — and it does not touch the failure TTLs, link permanence, the refresh gate or the in-flight attempt marker.

### Changed
- **Cached Music Index data is served stale-while-revalidate**: a row whose metadata is older than the refresh interval (or whose `mi_updated_at` is NULL) still renders instantly and then queues a background pull that runs on the plugin's `shutdown` handler — plain PHP, no cron and no loopback dependency, `ignore_user_abort()` so the write survives an ended request, and `fastcgi_finish_request()` only when the server actually offers it. A release that has never been seen still fetches inline on the first render, exactly like the old transient miss, and rows are never evicted at any age or any setting — so a Music Index outage can no longer turn an already-seen release into "Album/Song not found". Only page renders may queue a refresh: the Pro search box, both log beacons and the og: social preview never do (a burst of searches or hits must not fan out into Music Index traffic), though those gated contexts may still fill an absent row, which is the same API traffic the old transient fill cost. The positive Music Index transients are gone entirely — one query now serves both titles and the Fountain link — while failures stay in transients under the unchanged policy (1 hour for definitive 200/404 misses, 30 seconds for unreliable ones), remembered under the same keys as before, and a fixed bug in those keys: the "is a miss remembered?" check tested the stored empty array for truthiness, which is always false, so a known miss was retried every time; it now tests for presence.
- **Docs: the README's data-source paragraph describes the cache table, the admin-set serve-stale refresh and the failure transients instead of the old "12 hours for successes, 1 hour for failures" transients**, and the Pro feature list names the new Cache tab alongside the log and report tabs.

## Resolver (v4v-musiclink) — [1.22.20] - 2026-10-01

### Changed
- **When no direct Fountain link can be retrieved, the Fountain button now points at `https://fountain.fm/discover` instead of the bare `https://fountain.fm` homepage**: Fountain's site restructure moved its front door, so the bare homepage was no longer a useful place to land a visitor who wanted the release — and it is exactly where every button lands while a redeploy is being self-healed, which is when the link is most likely to be clicked. The new target is used by the render fallback itself and by the client-side modal that intercepts an unresolved link before opening it (the modal now matches the discover URL first and still matches the bare homepage, so a link an admin typed by hand keeps the same confirm-first behaviour). The settings help text, the plugin-header DevTools notes and the comments around the fallback all say `fountain.fm/discover` now. ### Security
